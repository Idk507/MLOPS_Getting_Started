**Working with Images & Containers in Docker**

This section covers the everyday operations and deeper concepts you need once you can run basic containers. Mastering these makes you efficient and helps avoid common beginner pitfalls.

### 1. Listing, Inspecting, and Removing Images & Containers

#### Listing

**Containers**
```bash
docker ps              # Running containers only
docker ps -a           # All containers (running + stopped)
docker ps -aq          # Only container IDs (useful for scripting)
docker ps --filter "status=exited"   # Filter by status
docker ps --format "table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Ports}}"
```

**Images**
```bash
docker images          # or docker image ls
docker images -a       # Include intermediate layers
docker images --filter "dangling=true"   # Untagged intermediate images
docker images --format "table {{.Repository}}\t{{.Tag}}\t{{.ID}}\t{{.Size}}"
```

#### Inspecting

`docker inspect` returns detailed JSON metadata.

```bash
docker inspect <container-or-image-name-or-id>
docker inspect --format='{{.State.Status}}' mycontainer
docker inspect --format='{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' mycontainer
docker inspect --format='{{.Config.Env}}' myimage
```

Useful things you can extract:
- Environment variables
- Mounted volumes
- Network settings / IP addresses
- Entrypoint / CMD
- Labels
- Resource limits
- Healthcheck configuration

#### Removing

**Containers**
```bash
docker rm <container>                 # Remove a stopped container
docker rm -f <container>              # Force remove (even if running)
docker rm $(docker ps -aq)            # Remove all containers
docker container prune                # Remove all stopped containers
```

**Images**
```bash
docker rmi <image>                    # Remove by name:tag or ID
docker rmi -f <image>                 # Force remove
docker image prune                    # Remove dangling images
docker image prune -a                 # Remove all unused images
docker system prune -a --volumes      # Nuclear option (be careful!)
```

**Best practice**: Prefer `docker container prune` and `docker image prune` over blanket `rm`/`rmi` commands in shared environments.

### 2. Tagging Images

An image is uniquely identified by its **ID** (content-addressable SHA256 hash). A **tag** is a human-readable pointer to that ID.

**Format**: `repository:tag`  
Examples:
- `nginx:latest`
- `nginx:1.25-alpine`
- `myregistry.com/myapp:1.2.3`
- `ghcr.io/username/project:sha-abc123`

#### Common tagging commands

```bash
# Tag an existing image
docker tag nginx:latest mynginx:v1
docker tag <image-id> myrepo/myapp:1.0.0

# Build with a tag directly
docker build -t myapp:1.0.0 .
docker build -t myapp:1.0.0 -t myapp:latest .

# Multiple tags at once
docker tag myapp:1.0.0 myregistry.com/myapp:1.0.0
docker tag myapp:1.0.0 myregistry.com/myapp:latest
```

#### Tagging best practices

| Practice                        | Why it matters                              |
|---------------------------------|---------------------------------------------|
| Avoid relying only on `latest`  | `latest` is mutable and can change unexpectedly |
| Use semantic versioning         | `1.2.3`, `1.2`, `1`                         |
| Add short Git SHA               | `1.2.3-abc1234` for traceability            |
| Include architecture if needed  | `myapp:1.0.0-amd64`                         |
| Prefer immutable tags in production | Never overwrite a tag that is already deployed |

When you push to a registry:
```bash
docker push myregistry.com/myapp:1.0.0
docker push myregistry.com/myapp:latest
```

### 3. Understanding Image Layers and the Build Cache

#### What are layers?

Every Docker image is a stack of **read-only layers**. Each instruction in a Dockerfile (`RUN`, `COPY`, `ADD`, etc.) usually creates a new layer.

Example mental model:

```
┌─────────────────────────────────────┐
│  Layer 4:  COPY app /app            │  ← Your application code
├─────────────────────────────────────┤
│  Layer 3:  RUN npm install          │  ← Dependencies
├─────────────────────────────────────┤
│  Layer 2:  WORKDIR /app             │
├─────────────────────────────────────┤
│  Layer 1:  FROM node:20-alpine      │  ← Base image (itself has layers)
└─────────────────────────────────────┘
```

- Layers are content-addressable (identified by hash).
- When you run a container, Docker adds a thin **writable layer** on top (the container layer). Changes made inside the running container live only in this writable layer unless you commit them.

#### Build cache

Docker tries to reuse existing layers whenever possible. This is the **build cache**.

How caching works:
1. Docker looks at each instruction in order.
2. If the instruction and all previous layers are identical to a previous build, it reuses the cached layer.
3. As soon as one instruction changes, **all subsequent layers are invalidated** and rebuilt.

**Cache-busting examples**:
```dockerfile
# Bad order (cache broken often)
COPY . .
RUN npm install

# Good order (dependencies cached unless package.json changes)
COPY package*.json ./
RUN npm install
COPY . .
```

**Useful cache-related commands**:
```bash
docker build --no-cache -t myapp .     # Disable cache completely
docker build --cache-from myapp:latest # Use another image as cache source
docker builder prune                   # Clean build cache
```

**Modern tip (BuildKit)**:  
With BuildKit enabled (default in recent Docker), you get better caching, parallel builds, and features like cache mounts:
```dockerfile
RUN --mount=type=cache,target=/root/.npm npm install
```

### 4. `docker commit` vs Proper Image Building

#### `docker commit`

```bash
docker commit <container> mynewimage:tag
```

This takes the current state of a **running or stopped container** (including the writable layer) and turns it into a new image.

**When people use it**:
- Quick experiments
- “I installed something manually inside the container, now I want to save it”

**Why it is generally a bad idea for real work**:
- Not reproducible — no record of how the image was created
- Bloated images (includes temporary files, package manager caches, etc.)
- Hard to version, review, or automate
- Violates infrastructure-as-code principles
- Difficult for teams to collaborate

#### Proper image building (Dockerfile)

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
USER node
CMD ["node", "server.js"]
```

```bash
docker build -t myapp:1.0.0 .
```

**Advantages**:
- Fully reproducible
- Version-controlled (the Dockerfile lives in Git)
- Easy to review and improve
- Works perfectly in CI/CD
- Benefits from layer caching
- Can use multi-stage builds for smaller, more secure images

#### Comparison

| Aspect              | `docker commit`              | Dockerfile (`docker build`)      |
|---------------------|------------------------------|----------------------------------|
| Reproducibility     | Poor                         | Excellent                        |
| Automation          | Difficult                    | Native in CI/CD                  |
| Image size          | Often larger                 | Can be optimized                 |
| Collaboration       | Hard                         | Easy (code review)               |
| Best for            | Quick throwaway experiments  | Everything else                  |
| Recommended?        | Almost never in production   | Always                           |

**Rule of thumb**:  
Treat `docker commit` the same way you treat `git commit -a` without a message — occasionally useful for a quick save, but never as your normal workflow.

### Quick Reference Cheat Sheet

```bash
# List
docker ps -a
docker images

# Inspect
docker inspect <name-or-id>

# Remove
docker rm -f <container>
docker rmi <image>
docker container prune
docker image prune -a

# Tag
docker tag source:tag target:tag

# Build properly
docker build -t myapp:1.0.0 .

# Avoid
docker commit <container> myimage   # ← prefer Dockerfile
```
